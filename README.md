# MaJETstik

![MaJETstik](majetstik-logo.svg)

**An end-to-end particle-physics simulation pipeline: from proton–proton
collision to analysis-ready ROOT file, in one command.**

MaJETstik chains the four standard tools of collider phenomenology —
**Pythia 8**, **Delphes**, **FastJet** and **uproot** — into a single
reproducible workflow, and documents every step well enough that someone new to
HEP simulation can follow what is happening and why.

```
   pp collision          detector              jets                analysis
 ┌───────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────────┐
 │   Pythia 8    │──▶│   Delphes    │──▶│   FastJet    │──▶│  NanoAOD + plots │
 │ hard scatter  │   │  tracking    │   │  anti-kT     │   │  flat ROOT tree  │
 │ parton shower │   │  calorimeter │   │  R = 0.4     │   │  uproot / ROOT   │
 │ hadronisation │   │ particle flow│   │ substructure │   │  matplotlib      │
 └───────────────┘   └──────────────┘   └──────────────┘   └──────────────────┘
     .hepmc            _delphes.root       _jets.root          _nano.root
```

## Quick start

On **lxplus** or any machine with CVMFS mounted, there is nothing to install:

```bash
git clone <this-repo> MaJETstik && cd MaJETstik
source setup_env.sh          # puts Pythia, Delphes, FastJet, ROOT on your PATH
python3 main.py              # 1000 events, all five stages
```

Just under a minute later you have:

```
data/
├── zee_jets.hepmc               generator output (full event record)
├── zee_jets_delphes.root        detector-level objects
├── zee_jets_jets.root           clustered jets + substructure
├── zee_jets_nano.root       ←   the analysis file: flat NanoAOD-like tree
├── zee_jets_provenance.json     seed, cards, software versions
├── logs/                        one log per stage
└── plots/                       six figures
```

Look at what came out:

```bash
python3 examples/read_output.py            # jets, event by event
python3 examples/read_output.py --readme   # what every branch means
```

In a hurry? `python3 main.py --events 200` finishes in about fifteen seconds.

[`docs/sample_output.md`](docs/sample_output.md) shows exactly what a correct
run prints and plots, so you can check yours against it.

## Theory overview

A short tour; the full version with equations and references is in
[`docs/theory.md`](docs/theory.md).

### What event generation is (Pythia 8)

A proton is not elementary — it is a seething bound state of quarks and gluons
sharing its momentum. When two protons collide at 13.6 TeV, almost every
collision is a soft glancing blow, but occasionally two constituent partons
scatter hard. That rare, high-momentum-transfer interaction is the **hard
scatter**, and it is the only part of the event perturbative QCD computes
exactly. Pythia draws the incoming partons from measured **parton distribution
functions**, then applies the matrix element for the process you asked for —
here $q\bar q \to \gamma^*/Z \to e^+e^-$, the Drell–Yan process.

Drell–Yan is the standard candle of hadron colliders: two isolated electrons
whose invariant mass peaks at the precisely known Z mass, 91.19 GeV. The final
plot in the quick start reproduces that peak, which is how you know the whole
chain is working.

### Parton shower and hadronisation

The hard scatter alone gives a Z and nothing else. Two things intervene before
anything reaches a detector.

**The parton shower.** Coloured partons radiate gluons, and the probability of
emitting a *soft* or *collinear* gluon is logarithmically enhanced — so much so
that at LHC energies these terms are of order one and a fixed-order calculation
fails. The shower resums them by treating emission as a Markov chain evolving
downwards in momentum scale. Radiation from the *outgoing* partons gives jets
their internal structure; radiation from the *incoming* ones, generated by
backward evolution, is what turns "Z → ee" into "**Z + jets**". The jets in the
default sample are initial-state-radiation jets.

**Hadronisation.** QCD confines: the potential between colour charges grows
linearly with distance, so free quarks never reach a detector. Pythia uses the
**Lund string model** — colour-connected partons are joined by a string whose
energy grows until it snaps by creating a quark–antiquark pair, repeating until
only real hadrons remain. One quark becomes tens of pions, kaons and photons.
This is precisely why jets need to be *defined*.

### Detector simulation (the Delphes concept)

A real detector sees electrical signals, not particles. Simulating that
properly with Geant4 — tracking every particle through every piece of material
— costs minutes of CPU per event. **Delphes** instead applies the *net effect*
parametrically, in milliseconds:

1. charged particles curve in the magnetic field;
2. tracks are reconstructed with an efficiency $\epsilon(p_T,\eta)$ and smeared
   by the tracker resolution;
3. energy is deposited in calorimeter cells of finite granularity and smeared
   by $\sigma_E/E = a/\sqrt{E} \oplus b$;
4. **particle flow** merges tracks and calorimeter deposits into one
   non-double-counted list of candidates — tracks where they are more precise,
   calorimeter where it is;
5. electrons, muons, photons and b-jets are identified with parameterised
   efficiencies; missing transverse energy is computed.

The result reproduces the resolutions and efficiencies that drive most
phenomenology. It does not model detector geometry or secondary interactions —
that is the trade.

### Jet clustering algorithms

Since a quark arrives as a spray of hadrons, "the jet" must be *defined*: which
particles belong to it. A usable definition must be **infrared and collinear
safe** — adding an infinitely soft particle, or splitting one into two
collinear ones, must not change the answer — or the perturbative prediction it
is compared with diverges.

All modern algorithms share one structure: repeatedly merge the closest pair
under

$$d_{ij} = \min\!\left(k_{T,i}^{2p}, k_{T,j}^{2p}\right)\frac{\Delta R_{ij}^2}{R^2}$$

with the exponent $p$ choosing the algorithm: $p = +1$ is $k_T$, $p = 0$ is
Cambridge/Aachen, and $p = -1$ is **anti-$k_T$**. Anti-$k_T$ is the LHC
standard because the negative power makes *hard* particles cluster first, so
jets grow outward from hard cores into nearly perfect cones whose boundaries
are insensitive to soft radiation — which is what makes them calibratable.
MaJETstik uses anti-$k_T$ with $R = 0.4$ by default.

We also compute two **substructure** observables:

- **N-subjettiness** $\tau_N$ — how well the jet is described by $N$ subjets.
  The ratio $\tau_{21} = \tau_2/\tau_1$ is the standard tagger for a boosted
  two-pronged decay (W, Z, H); $\tau_{32}$ for a three-pronged one (top).
- **Soft-drop mass** — the jet mass after recursively dropping soft,
  wide-angle radiation. Much closer to the mass of whatever made the jet, and
  far less sensitive to the underlying event and pileup.

### What NanoAOD is and why we use it

CMS's data formats form a ladder. RAW is the detector readout; AOD holds
reconstructed C++ objects and needs the experiment's software framework to open
at all. **NanoAOD** is the bottom rung: a single flat `Events` tree in which
every branch is a plain number or a variable-length array of plain numbers.
No custom classes, no dictionaries, no framework — `uproot`, `ROOT`,
`RDataFrame` or bare C++ can all read it, at 1–2 kB per event instead of ~1 MB.

The convention is `<Collection>_<variable>`, and all branches sharing a prefix
have the same length within an event. That one rule is the entire format, and
it is why NanoAOD-style analysis runs on a laptop. MaJETstik's output follows
the same convention, so everything you learn here transfers directly to real
CMS open data.

## Installation guide

### The supported path: CVMFS (lxplus and friends)

Every dependency — Pythia 8, Delphes, FastJet with contribs, HepMC3, ROOT,
uproot, awkward, numpy, pandas, matplotlib — is already built and available
through a CERN **LCG view** on CVMFS. `setup_env.sh` sources one:

```bash
source setup_env.sh
```

```
MaJETstik environment ready
  LCG view   : /cvmfs/sft.cern.ch/lcg/views/LCG_107/x86_64-el8-gcc11-opt
  project    : /path/to/MaJETstik
  python     : Python 3.11.9
  Delphes    : /cvmfs/sft.cern.ch/lcg/releases/delphes/3.5.1pre09-.../x86_64-el8-gcc11-opt
```

You must source it in **every new shell** — it only sets environment variables.

The default view targets **EL8, x86-64**. On a different OS, pick a matching
view and export it before sourcing:

```bash
ls /cvmfs/sft.cern.ch/lcg/views/                    # available releases
ls /cvmfs/sft.cern.ch/lcg/views/LCG_107/            # platforms for one release

export MAJETSTIK_LCG_VIEW=/cvmfs/sft.cern.ch/lcg/views/LCG_110/x86_64-el9-gcc13-opt
source setup_env.sh
```

Check it worked:

```bash
python3 -c "import pythia8, uproot; print('ok')"
which DelphesHepMC3 fastjet-config
```

### Installation without CVMFS

Four C++ projects must be built; none is pip-installable. Allow an hour or two.
Versions below are the ones MaJETstik is tested against.

**1. ROOT 6.34** — provides the C++ interpreter used to compile the FastJet
kernel at runtime, and PyROOT. Easiest via conda:

```bash
conda create -n majetstik -c conda-forge root=6.34 python=3.11
conda activate majetstik
```

**2. Pythia 8.313** — with Python bindings and HepMC3 support:

```bash
wget https://pythia.org/download/pythia83/pythia8313.tgz
tar xzf pythia8313.tgz && cd pythia8313
./configure --with-python-config=python3-config --with-hepmc3=/path/to/hepmc3
make -j8
export PYTHONPATH=$PWD/lib:$PYTHONPATH        # provides `import pythia8`
```

**3. HepMC3 3.2.7** — the event interchange format, with its Python bindings
(`pyHepMC3`), which `majetstik/hepmc.py` uses:

```bash
git clone https://gitlab.cern.ch/hepmc/HepMC3.git && cd HepMC3
cmake -B build -DHEPMC3_ENABLE_PYTHON=ON -DCMAKE_INSTALL_PREFIX=$HOME/hepmc3
cmake --build build -j8 && cmake --install build
```

**4. FastJet 3.4.3 + fastjet-contrib** — clustering, plus the `Nsubjettiness`
and `SoftDrop` add-ons:

```bash
wget http://fastjet.fr/repo/fastjet-3.4.3.tar.gz
tar xzf fastjet-3.4.3.tar.gz && cd fastjet-3.4.3
./configure --prefix=$HOME/fastjet --enable-allcxxplugins
make -j8 && make install

# contribs (Nsubjettiness, SoftDrop) built as ONE shared library, which is
# what majetstik/fastjet.py loads:
wget http://fastjet.hepforge.org/contrib/downloads/fjcontrib-1.101.tar.gz
tar xzf fjcontrib-1.101.tar.gz && cd fjcontrib-1.101
./configure --fastjet-config=$HOME/fastjet/bin/fastjet-config
make -j8 && make install && make fragile-shared-install
```

**5. Delphes 3.5.1** — the detector simulation:

```bash
git clone https://github.com/delphes/delphes.git && cd delphes
cmake -B build -DCMAKE_INSTALL_PREFIX=$HOME/delphes
cmake --build build -j8 && cmake --install build
export DELPHES_DIR=$HOME/delphes
export PATH=$DELPHES_DIR/bin:$PATH
```

**6. The Python packages** in [`requirements.txt`](requirements.txt):

```bash
pip install -r requirements.txt
```

Then make sure `PATH`, `LD_LIBRARY_PATH`, `PYTHONPATH` and `DELPHES_DIR` point
at all of the above, and that `MAJETSTIK_ROOT` is on `PYTHONPATH`. It is worth
writing your own `setup_env.sh` replacement that exports them.

### Optional: install the Python package

Only needed to `import majetstik` from code outside this directory:

```bash
pip install --user -e .
```


### Data flow

Measured on one lxplus core for the default 1000-event Z+jets run:

| # | Script | Reads | Writes | Time | Output size |
|---|--------|-------|--------|------|-------------|
| 1 | `generators/gen_pythia.py` | `.cmnd` card | `<run>.hepmc` | 23 s | 182 MB (182 kB/evt) |
| 2 | `simulation/run_delphes.py` | `.hepmc`, `.tcl` card | `<run>_delphes.root` | 8 s | 63 MB (63 kB/evt) |
| 3 | `analysis/cluster_jets.py` | `_delphes.root` | `<run>_jets.root` | 1 s | 1.4 MB |
| 4 | `analysis/write_nanoaod.py` | `_jets.root` + `_delphes.root` | `<run>_nano.root` | 7 s | 3.2 MB (3.2 kB/evt) |
| 5 | `analysis/analyze_jets.py` | `_nano.root` | `plots/*.png` | 2 s | six PNGs |

Generation dominates, and it scales linearly — 10 000 events takes about four
minutes. It is also trivially parallel; see `docs/extending.md`.

The HepMC file from stage 1 is by far the largest artefact (the full event
record, every parton and hadron). Delete it automatically with
`--drop-hepmc` once Delphes has consumed it.

## How to run

### Everything at once

```bash
python3 main.py
```

### One stage at a time

Each script is standalone, so you can run, inspect and re-run stages
individually while learning:

```bash
python3 generators/gen_pythia.py    --events 500 --seed 42 --run-name mytest
python3 simulation/run_delphes.py   --run-name mytest
python3 analysis/cluster_jets.py    --run-name mytest --jet-r 0.4
python3 analysis/write_nanoaod.py   --run-name mytest
python3 analysis/analyze_jets.py    --run-name mytest
```

Or select a range through `main.py`, which is the convenient way to re-run
after changing something:

```bash
python3 main.py --from 3          # re-cluster and redo stages 4-5
python3 main.py --to 2            # stop after the detector simulation
python3 main.py --only 5          # just remake the plots
```

### Configuration options

Every option has a command-line flag and a config-file key.

| Flag | Config key | Default | Meaning |
|------|-----------|---------|---------|
| `--run-name` | `run_name` | `zee_jets` | label for all output files |
| `--events` | `n_events` | `1000` | events to generate |
| `--seed` | `seed` | `12345` | master random seed (Pythia **and** Delphes) |
| `--pythia-card` | `pythia_card` | `generators/cards/zee_jets.cmnd` | the physics process |
| `--delphes-card` | `delphes_card` | `simulation/cards/majetstik_cms.tcl` | the detector |
| `--algorithm` | `jet_algorithm` | `antikt` | `antikt`, `kt` or `cambridge` |
| `--jet-r` | `jet_r` | `0.4` | jet radius |
| `--jet-pt-min` | `jet_pt_min` | `20.0` | minimum jet $p_T$ [GeV] |
| — | `softdrop_zcut`, `softdrop_beta`, `nsub_beta` | `0.1`, `0.0`, `1.0` | substructure parameters |
| `--no-truth` | `store_truth_particles` | on | drop `Particle_*` (smaller file) |
| `--drop-hepmc` | `keep_hepmc` | on | delete the HepMC file after stage 2 |
| `--no-plots` | `make_plots` | on | skip the figures |

Config files keep a study reproducible and self-documenting:

```bash
python3 main.py --save-config myrun.json    # write out the current settings
python3 main.py --config myrun.json         # run exactly that configuration
```

See [`examples/config_dijet.json`](examples/config_dijet.json) for a worked one.

### Worked examples

```bash
# QCD dijets with large-radius jets — where substructure actually does work
python3 main.py --config examples/config_dijet.json

# An ATLAS-like detector instead of CMS
python3 main.py --delphes-card $DELPHES_DIR/cards/delphes_card_ATLAS.tcl \
                --run-name atlas

# Compare jet algorithms on the same events (stages 3-5 only)
python3 main.py --run-name algo --events 2000 --to 2
for alg in antikt kt cambridge; do
  python3 analysis/cluster_jets.py --run-name algo --algorithm $alg
  python3 analysis/write_nanoaod.py --run-name algo
done
```

## Output format

`data/<run_name>_nano.root` contains a flat `Events` tree plus two
documentation objects:

```
├── Events      TTree      one entry per collision event
├── ReadMe      TObjString what every branch means
└── Metadata    TObjString full provenance as JSON
```

Headline branches — the complete list, with the jet→constituent map explained,
is in [`docs/output_format.md`](docs/output_format.md), and the same text is
embedded in every file (`python3 examples/read_output.py --readme`).

| Group | Branches |
|-------|----------|
| Jets | `Jet_pt`, `Jet_eta`, `Jet_phi`, `Jet_mass`, `Jet_nConstituents`, `Jet_btag`, `Jet_flavor`, `Jet_isLepton`, `Jet_genJetIdx` |
| Substructure | `Jet_tau1`, `Jet_tau2`, `Jet_tau3`, `Jet_softdrop_mass`, `Jet_softdrop_pt` |
| Constituents | `JetConstituent_jetIdx`, `JetConstituent_pfIdx`, `PFCand_*` |
| Leptons | `Electron_pt/eta/phi/charge/iso`, `Muon_pt/eta/phi/charge/iso` |
| MET | `MET_pt`, `MET_phi`, `GenMET_pt`, `GenMET_phi` |
| Truth | `Particle_pt/eta/phi/mass/pdgId/status`, `GenJet_*` |

> **Two things that surprise people.** Particle flow hands electrons to the jet
> algorithm, so a Z → ee event really does contain two "jets" that *are* the
> electrons — cut on `Jet_isLepton == 0` for a hadronic analysis. And
> `Jet_btag`/`Jet_flavor` are −1 when no Delphes jet matched, which is
> different from `Jet_btag == 0` ("not b-tagged").

## Example analysis

The complete minimal reader is [`examples/read_output.py`](examples/read_output.py);
[`examples/analysis_tutorial.ipynb`](examples/analysis_tutorial.ipynb) is the
guided version. The essentials:

```python
import uproot, awkward as ak, numpy as np
import matplotlib.pyplot as plt

with uproot.open("data/zee_jets_nano.root") as f:
    ev = f["Events"].arrays(["Jet_pt", "Jet_eta", "Jet_isLepton",
                             "Jet_tau1", "Jet_tau2", "Jet_softdrop_mass",
                             "Electron_pt", "Electron_eta", "Electron_phi",
                             "Electron_charge", "MET_pt"])

# 1. Jet pT spectrum, excluding the electrons particle flow handed the
#    jet algorithm (see the note above).
hadronic = ev["Jet_isLepton"] == 0
jet_pt = ak.flatten(ev["Jet_pt"][hadronic])
plt.hist(np.asarray(jet_pt), bins=50, histtype="step")
plt.yscale("log"); plt.xlabel(r"jet $p_T$ [GeV]"); plt.show()

# 2. The Z peak: invariant mass of the two leading electrons.
two = ak.num(ev["Electron_pt"]) >= 2
pt, eta, phi = (ev[f"Electron_{v}"][two][:, :2] for v in ("pt", "eta", "phi"))
px, py, pz = pt*np.cos(phi), pt*np.sin(phi), pt*np.sinh(eta)
E = np.sqrt(px**2 + py**2 + pz**2)                  # electrons are ~massless
m = np.sqrt((E[:,0]+E[:,1])**2 - (px[:,0]+px[:,1])**2
            - (py[:,0]+py[:,1])**2 - (pz[:,0]+pz[:,1])**2)
print("median m(ee) =", np.median(np.asarray(m)), "GeV   (PDG: 91.19)")

# 3. Substructure: the two-prong tagger.
tau1 = ak.flatten(ev["Jet_tau1"][hadronic])
tau2 = ak.flatten(ev["Jet_tau2"][hadronic])
good = np.asarray(tau1) > 0
tau21 = np.asarray(tau2)[good] / np.asarray(tau1)[good]
```

Stage 5 produces six figures in `data/plots/` automatically:

| Figure | What it shows |
|--------|---------------|
| `jet_pt.png` | reconstructed vs generator jet $p_T$ spectra |
| `jet_mass.png` | jet mass before and after soft-drop grooming |
| `jet_tau21.png` | the $\tau_{21}$ two-prong discriminant |
| `jet_response.png` | $p_T^{\rm reco}/p_T^{\rm gen}$ — the jet energy response |
| `jet_efficiency.png` | reconstruction efficiency vs generator jet $p_T$ |
| `dielectron_mass.png` | the Z peak |

## Reproducibility

A simulation you cannot repeat is not a measurement. MaJETstik makes a run
reproducible from a single integer.

**One seed drives everything.** `--seed` sets Pythia's `Random:seed` *and* is
injected as `set RandomSeed` into a derived copy of the Delphes card, since
Delphes smears energies with ROOT's global random generator. Same seed, same
cards, same events — bit for bit.

**Provenance is recorded twice.** `data/<run>_provenance.json` accumulates one
entry per stage, and the same record is embedded in the output ROOT file as the
`Metadata` object, so it cannot be separated from the data:

```json
{
  "stage": "cluster_jets",
  "seed": 12345,
  "cards": {
    "pythia_card": ".../zee_jets.cmnd",
    "pythia_card_checksum": "sha256:8f14e45f...",
    "delphes_card": ".../majetstik_cms.tcl",
    "delphes_card_checksum": "sha256:c4ca4238..."
  },
  "software": {
    "pythia8": "8.313", "delphes": "3.5.1pre09", "fastjet": "3.4.3",
    "root": "6.34.02", "uproot": "5.3.11", "numpy": "1.26.4",
    "python": "3.11.9", "majetstik_git": "0055f3d"
  }
}
```

Card **checksums** are stored, so a silently edited card is detectable. The
derived Delphes card is kept next to the output it produced.

**Everything is logged.** Each stage writes `data/logs/<stage>.log` with its
inputs, outputs, timings and physics summary.

**To repeat a run exactly:**

```bash
python3 main.py --config myrun.json        # or re-pass the same flags
```

Two caveats worth knowing. Results are reproducible for a *fixed software
stack* — a different LCG view means different Pythia or FastJet versions and
therefore different numbers, which is why versions are recorded. And when
running parallel jobs, **give each a different seed**; identical seeds produce
identical events and silently multiply your statistics by nothing.

- **See substructure actually work.** The default $R = 0.4$ jets from Z+jets
  are one-pronged, so grooming has nothing to remove. Run
  `python3 main.py --config examples/config_dijet.json` for 200 GeV QCD jets
  with $R = 0.8$ and compare `jet_mass.png`.
- **Turn the physics off, one piece at a time.** Set `PartonLevel:MPI = off`
  or `HadronLevel:Hadronize = off` in the Pythia card and watch the jet
  multiplicity and jet mass change. This is the fastest way to build intuition
  for what each modelling stage contributes.
- **Swap the detector.** `--delphes-card $DELPHES_DIR/cards/delphes_card_ATLAS.tcl`,
  or edit the magnetic field or calorimeter resolution in the MaJETstik card
  and watch `jet_response.png` widen.
- **Change the b-tagging working point** in the `BTagging` module of the card
  and see the b-tagged jet count move.
- **Add a substructure observable** — energy correlation functions, for
  instance — by extending the C++ kernel in `majetstik/fastjet.py`. Four small
  edits, described in `docs/extending.md`.
- **Generate a real physics sample**: $t\bar t$, $W \to \ell\nu$ (which gives
  genuine missing energy from the neutrino), or boosted tops at high $p_T$.
